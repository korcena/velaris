## Goal

Ship the deferred Phase 6 capabilities without regressing the 6.1 gate:

- **Real per-session worktree isolation** for OpenCode houses — fix the client, persist the
  worktree on the session, wire it behind the existing default-OFF flag, with allowlist and
  cleanup/orphan handling.
- **FTS5-backed archive search** as an additive external-content index with triggers, keeping the
  existing `LIKE` path working and as the fallback.
- **Per-agent cost rollups** grouped by `execution_sessions.agent_id` (NOT `usage_records` — that
  column does not exist) + read API + a small no-dependency UI surface.
- **Audit retention/export** — CSV/JSON export endpoint + configurable prune, respecting the
  engine single-writer rule.
- **`tasks.created_at` index** for board/list ordering and archive pagination.

## Global constraints (apply to every stage)

1. **Migrations are additive only.** `CREATE TABLE`, `ALTER TABLE … ADD COLUMN`, `CREATE INDEX`,
   and (for FTS) `CREATE VIRTUAL TABLE` + `CREATE TRIGGER`. No `DROP`, no rebuild, no in-file PRAGMA.
2. **FTS5 virtual tables are the one exception** — they are additive but do not appear in a Drizzle
   snapshot. They are created by a hand-written `drizzle-kit generate --custom` migration, are not
   modelled in `schema.ts`, and never alter an existing table. The FK-safe runner is unaffected
   (virtual tables have no FK relationships; `foreign_key_check` ignores them).
3. **Engine single-writer rule.** `execution_sessions`, `execution_events`, `approval_requests`
   transitions, and `notifications` are engine-only writes. Worktree columns live on
   `execution_sessions` → written by the engine. `audit_log` is a web user-action table; its export
   is a web read. Retention is placed in the **engine tick** (justified in the Open Questions table)
   because pruning `audit_log` is a periodic maintenance write that must not run concurrently from
   multiple web requests; it does not violate the rule (the engine may write tables it owns plus
   maintenance), and the web process never prunes.
4. **Zod schemas in `src/shared/schemas` are the single API-input source.** Any new endpoint's query
   is parsed there.
5. **`src/shared/**` stays React/Next-free; `src/app` must not import `src/engine`.**
6. **No dependencies.** CSV is serialized by hand (RFC-4180 minimal quoting); JSON is `JSON.stringify`.
7. **Animations transform/opacity only, reduced-motion safe** (the `globals.css` conventions).
8. **Gate order per stage:** `npx tsc --noEmit` → `npm test` → free port 3000 → `npm run test:e2e`.
   Baselines: tsc **0**, Vitest **1078**, Playwright **44** (all must stay green and only grow by
   the new assertions). Never `npm run lint`.

## Stage S1 — Real per-session worktree isolation (L) — the hard one

**Goal:** when `experimental.worktreeIsolation` is ON **and** the routed provider is OpenCode, each
execution runs in a fresh/reused git worktree rooted at the OpenCode worktree directory; the mapping
is persisted on the session; the worktree is reset on terminal and orphans are swept on boot.

### S1.1 OpenCode client fix (`src/server/opencode/client.ts`)

Replace the inert `worktree()` with three correct methods (pin the shapes that were live-verified;
add a `deleteWorktree` even though it is not required, because cleanup needs it):

```ts
export interface WorktreeInfo { name: string; branch: string; directory: string; }

/** POST /experimental/worktree {name?, startCommand?} → {name, branch, directory}. */
async createWorktree(opts?: { name?: string; startCommand?: string }): Promise<WorktreeInfo>;
/** GET /experimental/worktree → string[] (absolute worktree directories). */
async listWorktrees(): Promise<string[]>;
/** POST /experimental/worktree/reset {directory} → boolean. */
async resetWorktree(directory: string): Promise<boolean>;
/** DELETE /experimental/worktree {directory} → boolean (removes the worktree). */
async deleteWorktree(directory: string): Promise<boolean>;
```

- `listWorktrees` returns `string[]`; coerce non-array to `[]`.
- `resetWorktree`/`deleteWorktree` send `{directory}` and return `body === true` (tolerant: treat
  `{ok:true}`/any truthy as success).
- Update the module docblock's "verified endpoint set" list and remove the "inert scaffold /

### S1.4 Engine wiring (`src/engine/queue.ts` + `src/server/execution/runner.ts`)

The run directory is resolved in `TaskQueue.resolveWorkspace` (queue.ts:287-334) and passed as
`directory` into `executeTask` (queue.ts:270) / `runOllamaTask` (queue.ts:250).

**Design (minimal, flag-gated, OpenCode-only):**

1. In `runClaimedTask`, after `runtimeConfig` is resolved and **before** `resolveWorkspace`:
   - `const worktreeEnabled = provider === "opencode" && getWorktreeIsolationEnabled(raw);`
   - If enabled, call a new `resolveWorktree(db, client, house, runtimeConfig, task)` helper that:
     a. Resolves the real task directory against the **worktree-augmented allowlist** (see S1.5) so
        the original repo path is still validated.
     b. Creates a fresh worktree via `client.createWorktree({ name: <sanitized task id/slug> })`
        (or reuses the previous session's worktree for the same task when one is stored — see Q3).
     c. Returns `{ directory: info.directory, branch: info.branch }`.
   - If the worktree call fails, **fall back to the normal resolved directory** and emit an
     `execution_events` `error` payload (`{ error: "worktree create failed", detail }`); do **not**
     fail the task (isolation is best-effort, default OFF, never a regression when absent).
2. Pass `worktreeDirectory`/`worktreeBranch` into `RunContext`; `executeTask` calls
   `createExecutionSession` with them and stores them (or calls `setSessionWorktree` right after).
   `runOllamaTask` is **not** changed (Ollama never creates worktrees).
3. **Cleanup on terminal (Q3 recommended policy):**
   - On `completed`: `client.deleteWorktree(directory)` (remove); clear `worktree_directory` only if
     deletion succeeded — otherwise keep the row for the boot sweep.
   - On `failed`/`aborted`/`interrupted`: `client.resetWorktree(directory)` (preserve for inspection
     or reuse) and keep the mapping. Rationale: a failed run may need its worktree for debugging.
   - Never delete a worktree whose session is not terminal.
   - All cleanup is best-effort; a thrown error is logged, never propagated into the runner result.
4. **Boot-time orphan sweep (Q3):** in `src/engine/reconcile.ts` (or a new `sweepWorktrees(db, raw,
   client, log)` called from `main.ts` right after `reconcile`), when the flag is ON:
   - `listWorktrees()` → set `W`.
   - `listSessionsWithWorktrees(db)` → sessions with a stored directory.
   - For a worktree in `W` that is **not** referenced by any non-terminal session AND whose branch is
     `opencode/*`: `resetWorktree` + `deleteWorktree` (age guard: only delete if the directory mtime
     is older than a grace period, e.g. 1 hour, to avoid racing a just-created one). Log each action.
   - Never touch worktrees not under the OpenCode worktree root, and never touch non-`opencode/*`
     branches (branch-pollution guard).
   - Idempotent; skip entirely when the flag is OFF.

### S1.5 Allowlist interaction (the hard isolation problem) — Q2

Worktrees sit at `~/.local/share/opencode/worktree/<hash>/<name>`, outside every house allowlist.
`resolveSafePath` realpaths the candidate and requires prefix containment, so it **will** reject.

**Recommended strategy (single, documented exception):** when the worktree flag is ON, augment the
resolved allowlist used **only for the run directory** with the OpenCode worktree **root**
(`~/.local/share/opencode/worktree`) — not the whole home dir, not `/`.

- New helper in `src/lib/paths.ts` or `src/engine/worktree.ts`:
  `worktreeRoot(): string` → `${XDG_DATA_HOME ?? ~/.local/share}/opencode/worktree`, realpath'd if
  it exists.
- In `resolveWorkspace`, the allowlist used to validate the **final run directory** becomes
  `[...configuration.workspaceAllowlist, worktreeRoot()]` only when the flag is ON and provider is
  OpenCode. The **original** `task.workingDirectory` is still validated against the **house
  allowlist alone** first (so a task cannot point at an arbitrary dir just because worktree mode is
  on). Order: validate the source repo path against the house allowlist → create worktree → validate
  the worktree directory against the augmented allowlist (it will pass).
- The worktree root is a fixed OpenCode-owned location; exposing it as an allowlist entry is scoped
  and auditable. Document this exception in the queue and paths docblocks.
- Rejected alternative (per-house opt-in extra root, Q2 option B): more UI/schema surface and a
  migration, with no security benefit over a single engine-owned root. Not recommended.

## Stage S2 — FTS5 archive index scale-up (M)

**Goal:** an additive external-content FTS5 index over archive-searchable text, used automatically
when present, with the existing `LIKE` path retained as the default/fallback. **No regression** in
`tests/unit/archive-repo.test.ts` or `phase6-archives.spec.ts`.

**Q5 recommended:** keep `LIKE` as the default and use FTS as an **automatic-if-present** path for
the `q` clause only; non-text filters still use the existing SQL. If the FTS table/triggers are
missing (e.g. an older DB not yet migrated), silently fall back to `LIKE`. This guarantees no
behavioural regression and lets e2e (which seeds via `better-sqlite3` and boots web, which runs
migrations) exercise FTS after migration.

### S2.1 Migration `0010_*` (custom, hand-written)

`npm run db:generate -- --custom --name archives_fts` emits an empty `.sql`; hand-write it. Use an
**external-content** FTS5 table keyed to `tasks` (the archive result grain is a task), plus a
backfill and AFTER INSERT/UPDATE/DELETE sync triggers. Content spans task text plus the task's
artifact/message text through a denormalized join at trigger time is not possible in a trigger for
other tables — so choose one of these, recommended **option A**:

- **Option A (recommended): index `tasks` text only** (`title`, `description`), external-content
  `content='tasks'`, `content_rowid='rowid'`. Simple, deterministic, no cross-table trigger
  fragility. Loses artifact/message text from FTS matching; but the acceptance text ("task/house/
  text") is satisfied and the `LIKE` path still covers artifacts/messages for `q` when the FTS
  result is a superset? **No** — FTS-only `q` would be narrower. To avoid regressing the existing
  test that searches `RESULT-MARKER-55` and `MESSAGE-MARKER-49`, the `q` path must remain the
  `LIKE` union **unless** we also index artifacts/messages.
- **Option B (recommended after all, to preserve the tests): a standalone (non-external-content)
  FTS table `archives_fts(task_id UNINDEXED, title, description, artifact_text)`** populated by
  triggers on `tasks`, `artifacts`, `agent_messages`, and `execution_sessions` (the join key for a
  message → task). This requires careful triggers and a backfill, but keeps all four text sources
  and therefore keeps the existing assertions green while enabling FTS.

**Recommended decision for the plan: Option B**, because the existing golden tests explicitly assert
artifact and message text search; a task-only FTS would regress them. Keep the index **contentless
or standalone** (not external-content) so it can aggregate multiple source tables. Add:
- `CREATE VIRTUAL TABLE archives_fts USING fts5(task_id UNINDEXED, title, description, artifact_text, tokenize='unicode61');`
- Backfill: `INSERT INTO archives_fts(task_id,title,description,artifact_text) SELECT t.id,t.title,t.description, COALESCE((SELECT group_concat(a.content,' ') FROM artifacts a WHERE a.task_id=t.id),'') || ' ' || COALESCE((SELECT group_concat(am.content,' ') FROM agent_messages am JOIN execution_sessions s ON s.id=am.session_id WHERE s.task_id=t.id),'') FROM tasks t;`
- Sync triggers: `tasks_ai/tasks_au` recompute that task's row; `artifacts_ai/artifacts_au` and
  `agent_messages_ai/agent_messages_au` recompute the owning task's row. Deletes: delete the task's
  FTS row (and recompute on artifact/message delete). All triggers are `CREATE TRIGGER` (additive);
  `execute`-time idempotency is handled by the migration running once.

**Migration-safety interaction (spell this out in the plan and the migration header):**
- Virtual tables and triggers create **no FK relationships**, so `PRAGMA foreign_key_check` is
  unaffected (verified by probe).
- No `DROP`/rebuild of any real table.
- The FK-safe runner (`migrate.ts`) runs the whole chain in one transaction with FK OFF; `CREATE
  VIRTUAL TABLE`/`CREATE TRIGGER`/backfill `INSERT` are all legal inside that transaction
  (probed).
- The backfill runs at migration time, once; it is additive (creates no source rows).
- An `IF NOT EXISTS` guard is **not** needed because drizzle records the migration as applied; but
  the chain test may replay — keep DDL standard and rely on the applied-marker.

### S2.2 Repository (`src/server/repositories/archive-repo.ts`)

### S4.2 Retention/prune — engine tick (Q4 recommended)

**Placement justification:** pruning is a periodic maintenance write. The web process must not run
background timers that write the DB (it is not the execution writer, and multiple web requests could
race). The engine already runs a tick (`queue.ts`) and owns maintenance (`reconcile`). Put the prune
in the engine.

- Config source: `provider_configs.extra` is per-provider and a poor fit for a global policy. Prefer
  a dedicated key in `engine_state`-style storage or a new simple `app_settings` key/value table.
  **Recommended (least churn):** reuse `engine_state` with key `audit_retention_days` (value is a
  string; absent/FALSE = retain forever). It is a text key/value singleton table already shared by
  both processes and needs no migration. If a UI is desired, add a Settings card that writes this
  key via a small web route — but that is a web user-action write to `engine_state`, which is not
  owned by either process. **Safer alternative:** put the retention config in the default OpenCode
  provider `extra` (like the worktree flag) so the web already knows how to write it and audit it.
  **Recommended: `extra.audit.retentionDays` on the default OpenCode provider config**, reusing the
  existing worktree-flag pattern + Settings card + audit write. `0`/absent = keep forever (Q4
  default).
- New engine helper `pruneAuditLog(raw, retentionDays)` in `src/server/repositories/audit-repo.ts`
  or `src/engine/audit-maintenance.ts`: `DELETE FROM audit_log WHERE created_at < <cutoff>`.
  Never delete when retentionDays is 0/absent. Run once per engine boot then at most once per hour
  in the existing tick cadence (guard with an in-memory `lastPrunedAt`). Log the deleted count.
- **Safety:** default retention is **keep forever**; the setting must be explicitly enabled. The
  prune only deletes `audit_log` rows, never execution tables.

## Risks and mitigations

1. **Migration/data-loss (highest).** Every 6.2 migration is additive; FTS is the only virtual-table
   case and creates no FKs. Mitigation: `0009` is `ADD COLUMN`; `0010` is `CREATE VIRTUAL
   TABLE`/`TRIGGER` + backfill; extend the chain + real-DB guard tests; assert `foreign_key_check`
   empty; no in-file PRAGMA; no `DROP` of a real table.
2. **FTS triggers drift / missed updates.** A trigger that fails to recompute a task's row yields
   stale search results. Mitigation: standalone FTS with explicit recompute triggers on
   tasks/artifacts/agent_messages; a unit test that mutates each source and re-searches; the `LIKE`
   fallback remains for the no-FTS case.
3. **FTS query injection / syntax errors.** Raw user text in `MATCH` can throw. Mitigation: quote
   and escape tokens; a test with `"`, `*`, `-`, `%`, `_` must return 200, never 500.
4. **Worktree allowlist escape.** The worktree root is added to the run allowlist. Mitigation:
   validate the source repo against the house allowlist first; add only the exact worktree root;
   never add `$HOME`; tests assert an out-of-root path is still rejected.
5. **Orphaned worktrees / `opencode/*` branch pollution.** Mitigation: delete on success, reset on
   failure, boot sweep with a grace period that only touches unreferenced `opencode/*` worktrees
   under the root; never delete non-`opencode/*` branches.
6. **Worktree wiring regresses the flag-OFF path.** Mitigation: all worktree code is behind
   `getWorktreeIsolationEnabled` + provider `opencode`; a flag-off test asserts **no** worktree call;
   run `queue-loop`/`queue-ollama`/`queue-highlord`/`runner-status-machine`/`orchestrator`/`reconcile`.
7. **Engine single-writer violation.** Mitigation: worktree columns are engine-written; audit prune
   is engine-tick; export is a web read; no web route writes execution tables.
8. **`agent_id` change alters session semantics.** Populating it for default runs is additive but
   must stay nullable end-to-end. Mitigation: keep nullable; round-trip test; no existing code
   assumes null.
9. **CSV correctness.** Hand-rolled CSV can mis-quote. Mitigation: RFC-4180 unit tests with commas,
   quotes, newlines; a bounded row cap.
10. **Scope creep / dependency temptation.** Mitigation: explicit non-goals; reuse existing
    `extra`/Settings patterns; no new packages (verified by diffing lockfile).

## Rollback

- **Per stage.** Each stage is one commit (Q7) and its migration is additive. Roll back by reverting
  the commit. Because no 6.2 migration drops or rebuilds a table, a reverted code state still opens
  the newer DB safely: extra nullable columns/virtual tables are ignored by older code. Drizzle's
  `__drizzle_migrations` marker means a re-applied forward migration is idempotent; to fully undo
  DDL, apply a **new forward** migration (`DROP INDEX`/`DROP TRIGGER`/`DROP TABLE archives_fts`,
  which is safe only for the index/virtual table/triggers). Never edit an applied migration file.
- **FTS specifically.** `archives_fts` and its triggers can be dropped at any time; the repository
  automatically falls back to `LIKE` when the table is absent. This is the designed escape hatch.
- **Worktree specifically.** Turn the flag OFF: `getWorktreeIsolationEnabled` returns false, no
  worktree call is made, and execution is byte-identical to 6.1. The `worktree_*` columns remain
  (nullable, ignored). Orphaned worktrees can be reset/deleted manually from
  `~/.local/share/opencode/worktree`.
- **Retention.** Set `extra.audit.retentionDays` back to `0`/absent to stop pruning; export is
  read-only and has no rollback.
